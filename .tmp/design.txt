文档说明
本文档为智能填报系统的详细设计说明书，承接《智能填报系统需求规格说明书》，用于说明系统的总体架构、功能实现方式、数据库结构、接口约定、前端渲染规则、关键算法处理方案及非功能设计，作为开发编码、测试用例编写、系统评审与交付验收的技术依据。
文档中涉及的服务器数量、网络地址、组织编码等与具体环境相关的信息，以部署时的实际环境为准；涉及的业务规则若与最终确认的需求存在差异，以经双方确认后的需求基线为准。

1　概述
1.1　编写目的
本文档面向智能填报系统的开发实现阶段，将需求转化为可执行的技术设计，明确系统如何支撑“上级下发填报任务、下级单位在线填报、不同子单位表单内容不同、表单字段按部门与角色控制权限”这一核心业务目标。文档同时给出数据库结构、接口契约与关键算法处理方式，供开发、测试、运维及评审人员共同使用。
1.2　项目背景
集团内部存在大量周期性、临时性数据填报业务。以往由集团各职能部门以 Excel 模板线下下发，各子单位填写后逐级汇总，存在模板版本不统一、字段口径不一致、收集与核对工作量大、填报过程无法留痕、部分敏感字段不应向全部填报单位开放等问题。
建设智能填报系统后，由业务部门在系统内创建表单模板并下发填报任务，各子单位登录后按本单位适用的表单完成填报，系统按预置规则控制字段的可见性与可编辑性，并支持在线审核、进度跟踪与数据汇总导出，实现填报业务的线上化与规范化。
1.3　适用范围
本文档适用于智能填报系统的设计、开发、测试、部署与验收全过程。系统面向集团本部及下属子单位的内部用户，不面向外部单位开放填报入口；系统部署于集团内网环境，通过 VPN 支持外网接入访问。
本文档不包含统一身份认证平台的内部实现、短信网关与邮件服务的服务商侧配置，上述内容以接口对接方式引用，详见第 5 章。

2　总体设计
2.1　设计目标与原则
系统设计围绕四项基本目标展开：一是表单可配置，新增业务表单不需修改代码；二是表单可按填报主体差异化呈现，同一个填报任务在不同子单位看到的字段可以不同；三是字段级权限可控，同一张表单内不同部门、不同角色对字段的可见与可编辑范围可以不同；四是填报过程可追溯，模板版本、填报数据、审核意见与操作日志完整留存。
为实现上述目标，设计遵循以下原则。其一，动态表单采用元数据驱动，不为每张业务表单建立独立物理表，避免表单增多后结构失控。其二，同一模板只维护一份母版，子单位差异以规则表的形式叠加，避免模板被大量复制后难以统一调整。其三，权限校验以后端为准，前端渲染控制仅用于改善体验，不作为权限边界。其四，模板变更保留版本，历史填报数据按填报时点的模板版本呈现，保证数据含义不因模板调整而改变。
2.2　业务总体流程
业务流程自分发至归档共七个环节，各环节的主体与产出如下。
（1）模板创建：表单管理员在系统中新建表单模板，配置字段名称、字段类型、是否必填、校验规则与下拉选项，形成基础模板。
（2）差异与权限配置：管理员针对需要差异化的子单位配置字段隐藏、字段属性调整或独有字段，并按角色、部门配置字段权限。
（3）任务下发：管理员创建填报任务，选择表单模板，指定下发范围与填报起止时间，配置是否需要审核及审核人。
（4）表单加载：填报单位用户进入任务，后端按用户所属子单位合并基础模板与差异规则，叠加字段权限，生成表单 Schema 返回前端渲染。
（5）填报提交：用户填写表单，可保存草稿，确认后提交；提交时执行必填与格式校验，并按任务配置进入审核或直接生效。
（6）审核处理：审核人查看填报内容与附件，填写审核意见，执行通过或驳回；驳回后退回填报人修改。
（7）汇总归档：上级按单位、状态、时间筛选填报数据，查看填报进度并导出；任务截止后归档，数据只读留存。
2.3　系统架构
系统采用前后端分离的分层架构，自下而上分为数据层、应用层、接口层与前端层，并通过接入层统一处理身份与权限入口。
（1）接入层：部署统一网关，负责请求路由、限流与日志埋点；对接集团统一身份认证平台，实现单点登录与组织、用户信息同步。
（2）应用层：按业务划分为系统管理服务、模板服务、差异化配置服务、权限服务、任务服务、填报服务、审核服务、汇总服务与文件服务，服务之间通过内部接口调用，对外统一由网关暴露。
（3）数据层：MySQL 存储业务数据，Redis 缓存表单 Schema、组织架构与权限计算结果，MinIO 存储填报附件，三者均部署于内网。
（4）前端层：基于 Vue3 的单页应用，包含模板配置端、填报端与管理端；表单区域由 Schema 驱动动态渲染，不针对每张表单单独开发页面。
（5）定时任务：由调度组件承担任务到期提醒、超期未填报提醒、任务归档与统计宽表同步，避免在主业务链路中同步执行长耗时操作。

2.6　权限模型
系统权限分为功能权限与字段权限两类。功能权限控制菜单与按钮的可用性，按角色授予；字段权限控制表单中单个字段的呈现与编辑状态，按角色、部门、子单位分别授予，是本系统区别于普通表单系统的关键能力。
字段权限取值及前端处理方式如下：hidden 表示该字段不参与渲染；read 表示字段以只读方式呈现，可查看不可修改；edit 表示字段可正常编辑。未配置任何规则的字段按可编辑处理。
权限裁决遵循固定优先级：隐藏优先于只读，只读优先于可编辑；在同级对象中，用户级规则优先于部门级规则，部门级规则优先于角色级规则，角色级规则优先于子单位默认规则。即任一命中 hidden 的规则即决定该字段不可见，不再考虑其他规则。
2.7　部署架构
系统采用内网集中部署，应用与数据分离，前端静态资源由 Nginx 承载并反向代理后端接口。数据库与文件存储不对终端用户直接开放，仅允许应用服务器访问。

3　功能详细设计
3.1　组织与用户管理
组织管理以树形结构维护集团、子单位与部门，节点包含名称、编码、上级节点、排序与启停状态。单位编码全局唯一，作为填报数据归属判断与汇总分组的依据；调整组织层级不改变历史填报数据已记录的归属单位。
用户管理维护登录账号、姓名、所属子单位、所属部门与角色绑定关系。用户的所属子单位决定其可见的填报任务范围与表单差异视图；所属部门参与字段权限裁决。用户启停仅影响登录，不影响其历史填报数据的归属。
角色管理预置表单管理员、业务部门管理员、填报员、审核员四类角色，支持按需扩展。角色与用户为多对多关系，一个用户可同时具备填报与审核角色。
统一身份对接采用标准协议同步组织与用户基础信息，登录由统一平台发起，本系统仅校验令牌并建立本地会话，不在系统内单独维护密码。
3.2　表单模板管理
模板管理是表单能力的起点，包含模板新建、字段配置、预览、版本管理与状态变更五项功能。
（1）模板新建：录入模板名称、填报说明与所属业务分类，进入字段配置界面。字段以列表方式维护，支持拖拽调整顺序。
（2）字段配置：每个字段需定义字段标识、中文名称、字段类型、是否必填、校验规则与选项内容。字段标识在模板内唯一，一经保存不再变更，作为填报数据的存储键；中文名称可后续调整，不影响已填报数据。
（3）模板预览：可选择任一子单位预览表单呈现效果，用于在正式下发前核对差异配置与权限配置是否正确。
（4）版本管理：模板字段或规则调整后生成新的版本号，版本随保存动作递增并记录变更人、变更时间与变更内容摘要。已下发的任务继续沿用下发时绑定的版本。
（5）状态管理：模板状态分为草稿、启用、停用与归档。草稿不可下发；停用后不再允许新建任务，已在办任务不受影响。

3.3　子单位差异化配置
差异化配置用于解决同一填报任务在不同子单位字段口径不一致的问题。配置入口位于模板详情页，以“模板—子单位”为维度维护规则，不改动基础模板本身。
规则分为三类：一是隐藏基础字段，该字段在指定子单位不呈现；二是修改基础字段属性，可调整是否必填、选项范围、校验规则与默认值；三是新增独有字段，该字段仅在指定子单位呈现，其他单位不可见。
新增独有字段的字段标识需在该模板全部字段中保持唯一，系统在保存时执行唯一性校验，重复则拒绝保存并提示冲突字段。同一子单位对同一字段的多条规则以最后保存的规则为准，保存前系统按字段标识合并，不保留相互冲突的重复规则。
支持将某一子单位的差异规则批量复制到其他子单位，复制后仍可单独调整，便于同类单位快速配置。差异规则变更后，已提交的填报数据不回溯调整，历史数据按填报时点的规则呈现。
3.4　字段权限配置
字段权限配置以字段为维度，配置对象可为角色、部门或子单位。配置界面按字段列出已有规则，管理员可为同一字段添加多条规则，规则之间按第 2.6 节的优先级裁决。
配置时需注意三类典型场景。其一，审核人只读场景：将审核员角色对全部字段设置为 read，避免审核过程中篡改数据。其二，敏感字段隔离场景：将涉及薪酬、合同金额的字段对无资质部门设置为 hidden。其三，跨部门协同填报场景：同一张表单由多个部门分工填写，对各字段按部门分别设置 edit 与 read，实现分段填报。
权限配置的生效时点为表单加载时。后端在生成 Schema 时计算最终权限并随 Schema 下发；前端仅依据该结果渲染，不自行推断权限。
3.5　填报任务管理
任务管理负责把模板转化为一次具体的填报活动，主要包含任务创建、范围设定、周期设定、审核配置与归档五项功能。
（1）任务创建：选择模板与模板版本，录入任务名称与填报说明，指定下发单位。任务名称建议包含业务名称与期间，便于填报人在任务列表中识别。
（2）范围设定：从组织树中勾选允许填报的子单位。未在范围内的单位登录后不可见该任务，也不能通过接口直接提交数据，后端在提交时按任务范围二次校验。
（3）周期设定：设置填报开始时间与截止时间。开始时间之前任务呈待开始状态，不可填报；截止时间之后不可新增提交，已提交数据保留只读。
（4）审核配置：可选择不审核、单级审核或多级审核。不审核时提交即生效；单级与多级审核需指定审核人或审核节点，审核通过后数据进入汇总口径。
（5）归档：任务截止并完成汇总后由管理员归档，归档后任务与数据均为只读，操作日志继续保留。
3.6　在线填报
填报端是使用频率最高的界面，其设计重点是减少填报人的认知成本。任务列表按状态分组展示，分为待填报、草稿、已提交、已驳回四组，并显示截止时间与剩余天数。
进入填报后，后端按当前用户所属子单位合并模板与差异规则，生成字段列表，再逐字段裁决权限，输出 Schema。前端按 Schema 顺序渲染字段，对 hidden 字段跳过渲染，对 read 字段以只读样式呈现，对 edit 字段提供输入控件。
草稿保存支持手动保存与定时自动保存。自动保存默认每 30 秒触发一次，仅在表单内容发生变化时提交请求，避免无效写入。草稿记录独立标记，不进入汇总统计，也不触发审核流转。
提交时执行四类校验：必填校验、字段格式校验、附件的类型与数量校验、业务唯一性校验。校验不通过时定位到首个不满足的字段并给出提示，不提交数据。提交成功后记录提交时间与提交人，表单转只读；若任务配置审核，则进入待审核状态。
被驳回的填报可再次编辑，编辑范围限于当前用户具备 edit 权限的字段，驳回意见在表单顶部常驻显示，便于填报人对照修改。
3.7　填报审核
审核端以待办列表形式呈现，支持按任务、单位、提交时间排序。审核人可查看完整填报内容与附件，对每个字段的只读控制由权限规则保证。
审核操作包含通过与驳回。通过时数据状态变更为审核通过，进入汇总口径；驳回时必须填写审核意见，意见随记录保存并推送至填报人。多级审核场景下，通过后流转至下一节点，全部节点通过后数据才生效。
审核记录按节点顺序留痕，记录审核人、审核时间、审核结论与意见内容，不支持修改已提交的审核结论；如需变更结论，由管理员发起撤回并记录撤回原因。
3.8　数据汇总与导出
汇总视图以任务为单位，按子单位展示填报进度，包括应填报数、已提交数、审核通过数、驳回数与未填报数，并支持按单位、状态与提交时间筛选。
数据查看以宽表方式呈现，行对应填报记录，列对应模板字段，字段顺序与模板一致。差异字段的处理方式是：某字段在部分单位不存在时，该单元格留空并在表头标注适用单位范围。
导出支持按当前筛选结果导出 Excel，文件包含表头说明、数据区与导出时间。数据量较大时采用异步导出，生成文件后提供下载链接，链接有效期可配置，避免大文件长时间占用连接。
3.9　附件管理
附件与填报记录、字段标识绑定，同一字段可上传多个文件。上传时校验文件类型、单个文件大小与数量上限，超限即拒绝并提示。文件存储于对象存储，数据库仅保存文件标识与访问路径。
附件在填报提交前可删除与替换，提交后随表单转为只读，审核人与管理员可下载查看。为防止伪造，下载链接由后端签发短时有效凭证，不直接暴露存储路径。
3.10　操作日志与审计
日志覆盖登录、模板变更、差异与权限配置变更、任务下发、草稿保存、填报提交、审核操作、数据导出与附件下载八类行为，记录操作人、所属单位、操作对象、操作时间、来源地址与结果。
日志采用追加写入，不提供界面删除功能；按业务对象维度可回溯一条填报记录从创建到审核完成的完整链路，满足验收与审计要求。日志保留期限按建设单位数据留存规定执行。
4　数据库设计
4.1　设计原则
其一，动态表单不落物理业务表。表单字段以元数据形式存储，填报值按字段逐行存储，新增表单或新增字段均不需变更数据库结构。其二，模板、规则、任务、填报四类数据相互独立，通过外键逻辑关联，避免单表承载过多语义。其三，所有业务表统一包含逻辑删除标记与审计字段，便于数据追溯。其四，高频查询路径建立组合索引，避免全表扫描。
4.2　实体关系
组织与用户：一个子单位包含多个部门与多个用户；用户通过中间表关联角色。
模板与配置：一个模板包含多个字段，可对应多条子单位差异规则与多条字段权限规则。
任务与填报：一个模板可生成多个填报任务，一个任务可下发至多个子单位，一个子单位在一个任务下形成一条填报记录，一条记录包含多条字段值与多个附件。
日志：日志表按业务对象标识关联任务、记录与模板，不设强制外键，避免历史数据删除影响日志完整性。

4.6　数据存储策略
（1）填报值存储：采用按字段逐行的形式，新增字段不影响表结构；数字型字段额外写入数值副本列，用于排序、汇总与条件筛选，避免在文本列上做数值比较。
（2）附件存储：文件实体存于对象存储，数据库仅保存标识；删除填报记录时仅标记删除，不立即删除文件，由归档任务统一清理，避免误删导致证明材料不可追溯。
（3）汇总加速：任务数据量较大时，由定时任务将填报值行转列写入统计宽表，汇总查询优先读宽表；宽表可按任务重建，不作为权威数据源。
（4）备份策略：数据库每日全量备份、每小时增量备份，备份文件保留 30 天；对象存储启用多副本；备份恢复每季度演练一次并留存记录。
5　接口设计
5.1　通用约定
接口采用 RESTful 风格，请求与响应均为 JSON 格式，字符编码 UTF-8。除登录接口外，所有接口需在请求头携带访问令牌，令牌有效期默认 8 小时，超时需重新获取。
统一响应结构包含 code、msg、data 三个字段。code 为 200 表示成功，非 200 表示业务或系统异常；msg 为可直接展示的提示信息；data 为业务数据，列表接口统一返回 total、pages、list 结构。
分页参数统一为 pageNum 与 pageSize，pageSize 默认 20、上限 200，超出上限按上限处理。时间参数统一格式为 yyyy-MM-dd HH:mm:ss。

5.3　核心接口详述
5.3.1　获取表单 Schema
接口路径为 GET /api/form/schema，入参为 taskId 与 recordId（新建填报时为空）。该接口是差异化表单能力的关键，其处理顺序为：校验任务状态与单位范围、加载任务绑定版本的模板字段、加载当前单位的差异规则、合并生成字段列表、逐字段裁决权限、返回 Schema。
响应中每个字段包含 fieldKey、fieldLabel、fieldType、isRequired、sort、permission、config 七项。permission 取值为 hidden、read、edit，前端据此决定渲染方式；config 内含选项、校验规则、长度限制等渲染参数。
接口在首次访问时执行一次合并与裁决，结果按“任务标识 + 单位标识 + 用户标识”缓存，缓存有效期 10 分钟；模板、差异或权限规则发生变更时，由变更动作主动失效相关缓存，避免陈旧 Schema 影响填报。
5.3.2　保存草稿与提交填报
保存草稿接口为 POST /api/record/draft，入参包含 taskId、recordId（首次为空）与字段值列表。服务端在无记录时新建草稿记录，有记录时按字段标识增量更新，仅写入本次提交的字段值，未提交字段保持原值。
提交接口为 POST /api/record/submit，入参结构同草稿。服务端执行四项校验：任务是否在填报周期内、单位是否在任务范围、必填与格式是否满足、是否已超出允许的提交次数。校验通过后写入记录状态并冻结表单。
两个接口均需处理并发写入。同一单位同一任务在同一时刻只允许一个写入会话，服务端以“任务标识 + 单位标识”为键加分布式锁，锁超时 30 秒；提交成功后释放锁并清除该记录的 Schema 缓存。
5.3.3　审核操作
接口为 POST /api/audit/operate，入参包含 recordId、结论（pass 或 reject）、意见内容与当前节点标识。服务端校验操作人是否为本节点审核人、记录是否处于待审核状态，避免越权审核与重复审核。
驳回时审核意见为必填，长度限制 500 字；通过时若存在下一节点则流转，否则记录状态变更为审核通过并写入统计宽表同步队列。所有审核动作写入操作日志，记录节点、结论与耗时。

校验采用“即时提示 + 提交汇总”的方式。字段失焦时执行该项校验，提示定位在字段下方；提交时统一校验全部字段，失败则滚动至首个错误字段并高亮。

提交前弹出确认框，汇总展示本次填报的关键字段与附件数量，提示提交后不可自行修改；被驳回的记录在顶部显示驳回意见与驳回人，便于对照修改。
6.5　前端性能
（1）表单按需渲染：字段数量超过 60 个时按分组折叠，默认展开首组，其余组按需渲染。
（2）附件上传采用分片与并发控制，单个文件分片并发数不超过 3，避免内网带宽被占满。
（3）避免整表重渲染：字段值使用局部状态更新，仅在权限或字段集合变化时重建表单。
（4）静态资源按路由拆包，首屏仅加载工作台与填报列表所需资源。
7　关键算法与处理方案
7.1　表单合并算法
合并的目标是把“基础字段集合 + 本单位差异规则”转换为统一的字段列表，作为权限裁决与前端渲染的输入。处理步骤为：按版本加载基础字段并按 fieldKey 建立索引；加载本单位差异规则，按 fieldKey 归并；按差异类型执行隐藏、覆盖属性与新增；按 sort 重排并输出。
隐藏规则从字段列表中移除对应字段；覆盖规则仅替换属性，保留原 fieldKey 与创建顺序；新增规则向列表追加字段，其 fieldKey 与既有字段冲突时拒绝。合并过程中不修改基础模板数据，保证其他单位的视图不受影响。
7.2　权限裁决算法
裁决以字段为单位，输入为字段标识与当前用户的角色、部门、单位，输出为该字段的最终权限。处理顺序为：收集命中当前用户的全部规则；按对象优先级排序，依次为用户级、部门级、角色级、单位级；按权限严格程度递减顺序判断，hidden 命中即终止，read 命中则在无 edit 冲突时生效；无规则时返回 edit。
裁决结果参与缓存键的计算，缓存键包含模板版本、单位标识与用户标识，规则变更时按模板维度批量失效。
7.3　模板版本兼容
模板调整后生成新版本，填报记录在创建时记录 templateVersion，查看历史记录时按该版本加载字段定义与差异规则，不按当前版本呈现。任务在发布时冻结版本，任务执行期间的模板调整不影响在办任务，新版本仅对新建任务生效。
若模板删除某字段，历史数据仍保留在 form_record_data 中，导出时按历史版本呈现该字段并在表头标注“已停用字段”，避免历史数据看似缺失。
7.4　行转列处理
填报值按字段逐行存储，导出与汇总需转换为宽表。实现方式为：按记录聚合字段值，以模板字段顺序生成列；对缺失字段填空值；对多选值按分隔符拆分为可读文本；对附件字段输出文件数量与文件名摘要，附件实体单独打包或按链接提供。
单任务记录数超过 5000 条时，行转列在异步任务中执行，结果写入临时宽表后生成导出文件，避免在请求线程内完成大数据量转换。
7.5　并发与草稿机制
并发控制分两个层次：写入层以分布式锁保证同一单位同一任务同一时刻只有一个写会话；数据层以唯一约束兜底，防止锁失效时产生重复记录。锁获取失败时提示“该填报正在编辑中”，避免两人同时修改造成覆盖。
草稿采用定时保存与手动保存结合的方式，自动保存间隔 30 秒，且仅在内容变化时触发；草稿不写统计宽表，不触发提醒与审核流程；草稿超过任务截止时间后转为不可编辑，数据保留以便查阅。
7.6　填报唯一性控制
一单位一任务一条记录是默认规则，由任务配置项控制。开启时，同一任务下同一单位的记录唯一，允许多个部门协同填写同一记录，但提交动作仅允许一次；关闭时，同一单位可提交多条记录，用于按项目、按合同等明细型填报场景。
规则实现上，开启时对（task_id、org_id）建立唯一约束，并在提交时校验记录状态；关闭时由应用层生成记录序号，导出时按单位与序号排序，保证同一单位的多条记录可区分。

8.2　安全性设计
（1）身份与访问：统一认证或本地登录均签发短时令牌，令牌与设备指纹绑定，异常登录强制下线；接口按角色校验功能权限，按单位与部门校验数据范围。
（2）字段权限：所有字段级约束在后端二次校验，前端仅作呈现控制；提交接口逐字段比对 edit 权限，无权限字段的写入请求直接拒绝并记录日志。
（3）数据保护：密码以不可逆摘要存储；敏感字段在数据库中按需加密；导出文件包含水印与导出人信息，便于追溯扩散来源。
（4）上传与下载：上传校验扩展名、内容类型与文件头，禁止可执行文件；下载地址为短时签名地址，有效期默认 5 分钟。
（5）审计：关键操作全量留痕，日志不可通过界面删除；按季度导出日志归档，保留期限按建设单位规定执行。
8.3　兼容性设计
浏览器支持 Chrome 90 及以上、Edge 90 及以上，内网终端统一使用上述浏览器；不支持 IE 内核浏览器，避免因控件兼容问题影响填报。页面在 1366×768 与 1920×1080 分辨率下均可完整呈现，表格支持横向滚动。
服务端兼容 MySQL 8.0、JDK 17、主流国产化操作系统与中间件，具体品牌型号以建设单位采购与部署环境为准。
8.4　可靠性设计
应用服务双节点部署并前置负载均衡，单节点故障不影响访问；数据库主库按日全量备份、按小时增量备份，故障时按最近备份恢复，恢复目标为数据丢失不超过 1 小时。对象存储启用多副本，避免单盘故障导致附件丢失。
定时任务失败自动重试三次并告警；任务提醒失败不阻塞主流程，记录失败原因后由人工补发。
8.5　可扩展性设计
（1）字段类型可扩展：新增字段类型仅需扩展前端渲染组件与后端校验器，不影响存储结构。
（2）审核流程可扩展：当前支持单级与多级审核，预留流程引擎接口，后续可接入 Flowable 实现条件分支与并行审批。
（3）对接可扩展：预留组织同步、消息通知、单点登录与数据交换接口，便于与集团其他系统集成。
（4）部署可扩展：应用服务无状态，可按并发量横向扩容；文件存储与缓存可独立扩容。
8.6　可维护性设计
代码按模块分层，接口、服务、持久层职责清晰，避免业务逻辑散落在控制器；关键算法（合并、裁决、行转列）独立成组件并配套单元测试；配置项集中于配置文件，环境差异通过配置切换，不修改代码。

9.2　部署拓扑
终端用户经内网或 VPN 访问负载均衡地址，负载均衡将请求分发至两台应用服务器；应用服务器访问数据库、缓存与对象存储；对象存储与数据库不对外开放端口，仅允许应用服务器网段访问。系统不直接暴露于互联网。
9.3　上线与回退
上线按“数据库变更、应用发布、配置校验、冒烟验证”四步执行。数据库变更脚本先行执行并留存执行记录；应用采用停机窗口内滚动发布，单节点发布期间由另一节点承接流量；发布后执行冒烟用例，覆盖登录、Schema 加载、草稿保存、提交、审核与导出六项主流程。
回退方案为应用版本回滚至上一发布包，数据库变更采用兼容式设计，新增字段与新增表不影响旧版本运行，因此回退不需回滚数据库结构；若涉及数据修正，按备份点恢复并记录影响范围。
9.4　数据初始化
初始化内容包括组织树、部门、角色、管理员账号与基础字典。组织与部门按建设单位提供的清单导入，导入前校验单位编码唯一性；管理员账号首次登录强制修改密码；字典项按业务分类预置，后续由管理员维护。

function buildSchema(taskId, user):
  task = loadTask(taskId)
  baseFields = loadFields(task.templateId, task.templateVersion)
  diffs = loadDiffs(task.templateId, user.orgId)
  fields = mergeFields(baseFields, diffs)
  rules = loadPermRules(task.templateId)
  for f in fields:
    f.permission = decidePerm(f.fieldKey, rules, user)
  sortBy(fields, sort)
  return {taskId, taskName, templateVersion, fields}
function decidePerm(fieldKey, rules, user):
  matched = filter(rules, r -> r.fieldKey == fieldKey and matchTarget(r, user))
  if any(matched, perm == hidden): return hidden
  if any(matched, perm == read): return read
  return edit
